# Ditto things-search on PostgreSQL — Phase-0 benchmark

This document is the self-contained methodology + results summary for the PostgreSQL search
benchmark ("Phase 0" of the things-search-on-PostgreSQL evaluation). It is written so it can be
handed to someone who was not involved, or used directly as the storyline for a presentation.
`run-benchmark.sh` in this directory reproduces the whole series with one command.

**Question the benchmark answers:** can PostgreSQL serve Ditto's things-search workload — RQL
queries (eq/range/like/sort/count) on *arbitrary, undeclared* JSON paths, with per-field
authorization — at acceptable latency, given that PostgreSQL has no equivalent of MongoDB's
wildcard (`$**`) index?

**Verdict (reduced scale, provisional):** yes. Raw first-attempt latencies red-flagged three of
five query shapes (multi-second p95), but all causes were identified and mitigated with standard
PostgreSQL levers; with the mitigation stack applied, **every measured shape lands at 48–87 ms
warm p95 at 1M things** — under the 200 ms bar. The write path sustained ~180 updates/s of
full-document re-flattening with zero errors. Caveat: measured at 1M things / ≤10-minute write
windows; the full 10M / ≥1h bloat-plateau run is a scheduled follow-up, not yet executed.

The harness is a de-risking spike, not production code: it targets a throwaway
`search_things` / `search_flat` schema that mirrors the planned design — a JSONB document row
per thing (truth + authorization trees) plus a flattened `(thing_id, path, typed value)` side
table replacing Mongo's wildcard index.

## 2. Environment

- PostgreSQL 16, stock Docker image, long-lived container `ditto-search-bench-pg` on host port
  55432 (`bench`/`bench`/`bench`). The corpus must survive across stages, so this is deliberately
  **not** an ephemeral Testcontainers instance.
- Two memory profiles: container defaults for the raw runs (E0/E1), then laptop-class settings
  `shared_buffers=4GB, effective_cache_size=12GB, work_mem=64MB` from experiment E2 onward.
  GIN/autovacuum knobs stay at defaults and are recorded in each write-bench results file.
- Hardware: developer laptop (Apple Silicon, Docker VM). Absolute numbers are
  environment-specific; the *relative* effects (which lever fixes which shape, and why) are the
  transferable result.
- Disk: the 1M corpus needs ~30 GB in the Docker data volume (`search_flat` + indexes alone are
  ~27 GB); the write bench adds several GB of churn. Budget **≥ 40 GB free**.

## 3. Corpus

Generated by `CorpusGenerator` — fully deterministic from `(seed, index)`, so the same seed
always produces the byte-identical corpus (default seed 42, default count 1,000,000; both
overridable). Per thing:

- 5–50 attributes and 1–20 features (counts skewed low), mixed value types: strings, ints,
  doubles, booleans, nulls, 2–3-level nested objects, arrays (incl. arrays of objects and
  occasional arrays of arrays).
- Namespaces Zipf-skewed over a pool of 50.
- Two "hot" paths present in most things, giving both selective and unselective predicates:
  `/attributes/location/city` (string) and `/features/env/properties/temperature` (number).
- Authorization: 1–5 `global_read` subjects from a pool of ~200, plus grant/revoke trees shaped
  like production policy imprints.

At 1M things this yields **68,513,542 flattened leaf rows**. Bulk load (COPY things, COPY flat
rows, build indexes after load, ANALYZE) completes in ~9.4 minutes.

## 4. Method

Four stages, each a plain JUnit class whose name intentionally matches no Surefire/Failsafe
pattern — CI never runs them; they only run when invoked explicitly.

| Stage | Class | What it measures |
|---|---|---|
| 0.1 Load | `CorpusLoadBench` | COPY-based bulk load + index build + sizes |
| 0.2 Read (raw) | `ReadPathBench`, `PlanShapeComparisonBench` | 5 canonical query shapes; EXISTS-chain vs semi-join translation strategies |
| 0.2b Mitigations | `MitigationBench` | Cumulative ladder E0→E5 recovering the red-flagged shapes |
| 0.3 Write | `WriteFanoutBench` | Sustained full re-flatten upsert churn; v1 blanket rewrite vs v1.5 anti-join |

Measurement protocol (identical across read stages):

- **3 warmup + 20 timed executions** per shape, reporting p50/p95/max.
- Binds are **varying but deterministic** per iteration — no query-result caching artifacts, yet
  bit-for-bit reproducible runs.
- One representative **`EXPLAIN (ANALYZE, BUFFERS)`** plan captured per shape and committed with
  the numbers, so every latency claim is traceable to a plan.
- Every run **rewrites its committed results file** under
  `src/test/resources/bench/results/` — the evidence in git is always the output of the code in
  git.
- Each experiment runs as a fresh JVM (`mvn test` per class/method); mitigation experiments are
  strictly ordered because each assumes the previous one's schema/settings changes are in place.
- `MitigationBench` pins custom plans (pgjdbc `prepareThreshold=0`) — a deliberate, documented
  deviation forced by a real finding: after E1's statistics improvements, PostgreSQL's plan cache
  flipped a repeated prepared statement to a "cheap-looking" generic plan that executed at
  55 s vs 0.4 s custom-planned (`results/mitigations/e1-generic-plan-flip-evidence.md`). This is
  itself a production-relevant result for r2dbc statement caching.

The five read shapes (auth + global-read filters included unless noted):

1. **eq two-predicate AND** — the bread-and-butter search query.
2. **gt range** on a numeric path (control shape — always healthy).
3. **ilike** (RQL `like`/`ilike` → trigram GIN), on a low-cardinality path and a
   high-cardinality path.
4. **sort by arbitrary path + keyset paging** (page 1, OFFSET-100, keyset-100).
5. **count(*)** with auth filter (same WHERE as shape 1).

## 5. Headline results (1M things, warm cache)

### Raw (before mitigation) — three red flags

| Shape | p50 / p95 (ms) | Verdict |
|---|---:|---|
| 1: eq AND | 6,462 / 6,905 | RED FLAG |
| 2: gt range | 168 / 178 | pass |
| 3: ilike low-card | 71 / 126 | borderline (run-to-run unstable) |
| 3: ilike high-card | 2,298 / 2,405 | RED FLAG |
| 5: count + auth | 5,802 / 6,603 | RED FLAG |

Root causes (all traced to committed EXPLAINs, all *statistics/index* problems — none
architectural): (1) per-column statistics can't model value distributions *per JSON path*, so
the planner mis-estimated flat-row cardinality 38–80×; (2) the resulting plans did 14k–90k
random doc-row probes for the per-candidate auth recheck; (3) the table-wide trigram index isn't
path-scoped.

### Mitigation ladder E0→E5 (cumulative p50/p95 ms)

| Experiment | shape 1 | shape 2 | shape 3 high-card | shape 5 |
|---|---:|---:|---:|---:|
| E0 baseline re-measure | 7,222 / 8,424 | 169 / 176 | 2,092 / 2,294 | 7,095 / 8,367 |
| E1 statistics targets | 135 / 536 | 185 / 197 | 247 / 1,018 | 135 / 530 |
| E2 + realistic memory | 53 / 818 | 199 / 215 | 248 / 1,753 | 44 / 49 |
| E3 + covering indexes | 52 / 1,549 | 61 / 238 | 245 / 1,903 | 38 / 43 |
| E4 + path-scoped partial trigram | 48 / **87** | 57 / **71** | 22 / **49** | 45 / **50** |
| E5 rescue CTE (shapes 1/5) | 40 / **48** | — | — | 39 / **41** |

Honest negatives are part of the result: E1 alone barely moved the estimates (33.9× still wrong)
but surfaced the generic-plan-flip hazard; E3 covering indexes did *not* help the auth-heavy
shapes (their cost is the doc-row probe, not the index lookup) and were dropped again before the
write bench. The decisive levers: **E4** (51 MB path-scoped trigram index vs 304 MB table-wide;
ilike p95 2,294 → 49 ms, ~47×) and **E5** (materialized selective-leg CTE: 6.3× fewer buffer
reads, **43.2× faster cold start** — 3,441 ms → 80 ms, measured via symmetric container-restart
probes). E5 is the chosen production translator strategy.

Also measured: EXISTS-chain beats semi-join translation ~1.3–4.5× across 2/3-predicate mixes,
and a two-predicate AND uses the index on *both* legs — something a Mongo wildcard index cannot
do (it serves one predicate field per query).

### Write path (10-minute sustained run, 16 workers, target 200 upd/s)

Workload: full re-flatten of a 500-leaf thing per update — doc-row upsert + blanket
DELETE/unnest-INSERT of ~500 flat rows, one transaction per update.

- **107,495 transactions, 0 errors; achieved 179.2 upd/s** (target 200); txn latency p50 20 ms /
  p95 112 ms.
- WAL: ~66.6 GB over 10 min (~113 MB/s) — the expected write amplification of blanket rewrite.
- **Standout finding:** a single default-configured autovacuum worker could not keep pace —
  one vacuum cycle ran continuously through the entire run without finishing (dead tuples
  climbed 5.3M → 45.5M). This is *the* documented reason the ≥1h plateau gate needs autovacuum
  tuning and/or the v1.5 anti-join write shape (which deletes/rewrites only changed rows).
- Disclosed gap: the write-bench twin is all-numeric, so trigram/text index write cost is not
  measured by this run.

## 6. Reproducing

One command (from the repo root or from this directory):

```bash
internal/utils/search-r2dbc/benchmark/run-benchmark.sh all          # full series, ~2-3 h, ≥40 GB disk
internal/utils/search-r2dbc/benchmark/run-benchmark.sh all --quick  # demo-scale smoke (~15 min)
```

Stages can be run individually (they build on each other in this order):

| Stage | What it does | Approx. duration (1M) |
|---|---|---|
| `up` | Start the bench PostgreSQL container + wait ready | seconds |
| `build` | `mvn install -DskipTests` this module + deps (guards against a stale local repo from a sibling worktree) | minutes |
| `load` | Corpus generate + COPY + index build + ANALYZE | ~10 min |
| `read` | `ReadPathBench` + `PlanShapeComparisonBench` (raw numbers) | ~45–90 min (red-flag shapes are slow *by definition* here) |
| `mitigations` | E0→E5 in order, incl. the automated E2 container-recreate (memory settings, data volume preserved) | ~30–60 min |
| `fixround` | Optional evidence-fix methods + the two cold-start probes (container restart before each) | ~10 min |
| `write` | Write fan-out Part 0 (drop E3 indexes) → Part 1 (10 min sustained) → Part 2 (2×5 min blanket vs anti-join) | ~25 min |
| `down` | Remove the container (`--purge` also deletes the data volume) | seconds |

Knobs: `--count N` / `--seed N` (corpus), `--yes` (skip confirmation), `--quick` (50k corpus +
short write windows — for demos only, numbers are not comparable), `MVN=<path>` to pick a Maven
binary, `BENCH_PORT` to move the host port. Results land in
`src/test/resources/bench/results/` as markdown, overwriting the committed evidence — diff them
against git to compare your run with the recorded one.

Prerequisites: Docker with ≥40 GB free in its data volume, JDK + Maven able to build this repo,
and the module built once (`build` stage does it). The smoke test
(`PostgresSearchBenchSmokeIT`, stage `smoke`) verifies the flattening rules on a small
Testcontainers instance and is safe anywhere.

## 7. Caveats — read before quoting numbers

1. **Reduced scale:** everything above is 1M things / warm cache / ≤10-minute write windows.
   The plan's original gate is 10M / ≥1h with a bloat *plateau*; that run is scheduled, not done.
   Every "pass" is provisional at that scale.
2. **Environment-specific:** laptop-class Docker; treat latencies as relative evidence for the
   design levers, not as capacity planning input.
3. **High-cardinality ilike** is fixed by *path-scoped* trigram indexes (E4 proved the
   mechanism on one hot path); the general strategy for choosing scoped paths is a design
   decision still open at implementation time.
4. **Trigram/text write cost** under churn is unmeasured (all-numeric write-bench twin).

## 8. Presenting this

A storyline that has worked, mapping one slide per section above:

1. **The problem** — Mongo `$**` wildcard index has no PostgreSQL equivalent; GIN-on-JSONB is
   equality-only (§ intro, plan doc §2).
2. **The design under test** — doc row + flattened side table = what a wildcard index is
   internally, as rows (§1).
3. **Method** — deterministic 1M corpus, 5 shapes, warmup+timed, every number traceable to a
   committed EXPLAIN (§3–4). This slide buys credibility.
4. **Raw results** — three red flags; and *why* (statistics-per-path, auth probes, unscoped
   trigram) (§5).
5. **The ladder** — E0→E5 table; call out the negatives (E1, E3) as honesty markers and the two
   decisive levers (E4, E5) (§5).
6. **Write path + caveats** — 179 upd/s clean, autovacuum finding, reduced-scale disclaimer
   (§5, §7). End on the verdict and the scheduled 10M/≥1h follow-up.

For a live demo, `run-benchmark.sh all --quick` fits in a coffee break; show a `results/*.md`
file and its EXPLAIN afterwards rather than waiting on the full corpus.
