- **Date:** 2026-06-01
- **Scope:** Round 2 audit on branch `postgres-190626-feat-dev`, auditing remediation commit **`2b44232333`** ("address Postgres backend critical-review findings"). Round 1 confirmed 42 issues against `409d7e784e..e8fc36324f`; this round audits **what round 1 missed** and **what the remediation got wrong**, against the current working tree.
- **Method:** multi-agent fan-out — 10 critical finders (round-1-fix-verify, Pekko lifecycle, reactive/concurrency, serializer seam, actor wiring, SQL/schema/migrator, security/resources, observability/lifecycle, config/HOCON/ops, test quality), each finding independently re-verified by an adversarial verifier against the current tree (Verdict + re-rated severity + evidence), then synthesised and de-duplicated here.
- **Funnel:** **66 raw findings → 65 confirmed → 1 rejected → 0 already-fixed.** Of the 65 confirmed, **1 is a regression introduced by `2b44232333` itself**; the remainder are **new gaps round 1 missed** (the remediation touched the cited files but did not address them). ## 1. Verdict

**NOT mergeable. The backend is non-functional for real entity traffic, and round 1 missed why.**

Round 1 correctly fixed the *boot constructor* blocker and the persistence-math core. But round 1 (and the remediation) only ever exercised the journal/snapshot plugins via hand-built `JsonObject`/`String` payloads — never through a real Ditto **event adapter** or **snapshot adapter**, and never through three of the four entity actors. Round 2 shows the consequence:

1. **No Postgres event adapter exists and the profile binds none** (Critical, NEW). Pekko's default identity adapter hands the journal a raw domain `ThingEvent`/`PolicyEvent`; `toJsonText` throws on the first real write, the persistent actor stops, and replay returns a bare `String` the actor cannot match. This is the journal-side twin of the already-tracked snapshot-adapter gap (`ditto-postgres-2yg`) and is invisible to all 124 unit + 28 IT because the tests bypass the adapter seam.
2. **Three of four entity actors hardcode Mongo plugin IDs** (Critical, NEW). Only `ThingPersistenceActor` consults `PersistenceBackendProvider`; Policy/Connection/WoT write to Mongo regardless of the active profile while `auto-start-*` eagerly builds idle Postgres pools — silent split-brain.
3. **Schema bootstrap and `ddl-credentials` are entirely unwired** (High, NEW). No production path calls `PostgresSchemaManager.bootstrap()`; a fresh DB has no tables and the first query fails "relation does not exist." The advertised DDL-role privilege separation is dead config.
4. **The remediation introduced a sequence-number regression** (High, REGRESSION). `deleteMessagesTo`'s new INSERT branch writes `highest_sn = toSequenceNr`, violating the class's own stated HWM invariant; the new green test only asserts the UPDATE branch.

**What specifically blocks merge:** all four Critical items and the four High items in §2/§3 below. The persistence *arithmetic* core (HWM upsert, GIN tag containment, snapshot idempotency, advisory-lock DDL) remains solid and verified — but it cannot be reached by a real actor on the Postgres profile until the adapter seam and entity-actor wiring land.

## 2. Critical

### NEW (round 1 missed)

#### C-1. No Postgres event adapter exists and the profile binds none — every real entity write throws, every replay drops the event
*Lenses: pekko-lifecycle, serializer-seam, actor-wiring, round1-fix-verify (4 independent confirmations).*
- **Write path:** `ops/PostgresJournalOps.toInsert` (`PostgresJournalOps.java:164-189`) unwraps a `Tagged` payload but otherwise passes the bare value to `toJsonText`, which accepts only `JsonValue`/`CharSequence` and `throw new IllegalArgumentException` for anything else. Every `ditto-postgres-*-journal` block in `ditto-postgres-persistence.conf:129-205` declares only `class`/`plugin-dispatcher`/`entity` — **no `event-adapters`/`event-adapter-bindings`** (contrast the Mongo block `things.conf:626-635` binding `ThingMongoEventAdapter`). No `*EventAdapter` class exists anywhere under `persistence-r2dbc` (verified by `find`). With no binding, Pekko's `IdentityEventAdapter` hands the raw domain `ThingEvent`/`PolicyEvent` to `toInsert` → `toJsonText` → throws → `WriteMessageFailure` → actor stops.
- **Replay path:** `toRepr` (`PostgresJournalOps.java:191-195`) builds a `PersistentRepr` from the raw JSONB `String`; with no `fromJournal` adapter, the actor's recovery `match(getEventClass(), …)` (`AbstractPersistenceActor.java:153-158`) never matches a `String`, so every replayed event is silently dropped and the actor recovers with empty/stale state.
- **Tag corollary (High, see H-?):** without the adapter's `toJournal` calling `getJournalTags`, events persist with `tags = Set.of()`, so `PersistencePingActor` can never re-activate always-alive entities — see **H-5**.
- The Mongo adapter cannot be reused: `AbstractMongoEventAdapter.toJournal` emits a `BsonValue` (rejected by `toJsonText`) and its `fromJournal` only decodes `BsonValue` (cannot read JSONB text). Confirmed NOT addressed by `2b44232333` (commit edited the conf but added no binding).
- **Why green tests miss it:** `PostgresPluginLifecycleIT.BootTestActor` persists a hand-built `JsonObject` and recovers via `match(String.class, …)` (`PostgresPluginLifecycleIT.java:196,207`) — it deliberately models the *post-adapter* payload and never drives a real adapter; `PostgresParityMatrixIT` writes pre-serialized JSON straight into `writeMessages` (`:194-206`).
- **Fix:** add an `AbstractPostgresEventAdapter` (peer of the Mongo one) per entity whose `toJournal` returns `new Tagged(toJournalJson(event).toString(), getJournalTags(event))` and whose `fromJournal(text, manifest)` decodes via `GlobalEventRegistry`; add `event-adapters`/`event-adapter-bindings` to every `ditto-postgres-*-journal` block. Track at the same priority as `ditto-postgres-2yg`.

#### C-2. No per-service Postgres snapshot adapter exists — snapshot save and load both break for every entity
*Lenses: actor-wiring, pekko-lifecycle (#3 gated by this).*
- Only the backend-neutral `internal/utils/persistence/.../serializer/PostgresSnapshotAdapter.java` exists; no `ThingPostgresSnapshotAdapter`/`PolicyPostgresSnapshotAdapter`/`ConnectionPostgresSnapshotAdapter`/WoT variant anywhere (verified by `find`). Service config still names the Mongo adapter (`things.conf:19` `ThingMongoSnapshotAdapter`). The profile is honest — `ditto-postgres-persistence.conf:24-31,59-91` documents the override as a **required manual operator step** with only a commented template.
- **Save:** `PostgresSnapshotStoreOps.toJsonText` (`:114-126`) accepts only `JsonValue`/`CharSequence`/`byte[]` and throws on the `BsonValue` that `AbstractMongoSnapshotAdapter.toSnapshotStore` produces; worse, `saveAsync` (`PostgresSnapshotStoreOps.java:68-75`) calls `toJsonText`/`extractLifecycle` **eagerly, outside any Mono**, so the failure is a *synchronous throw* rather than the failed Future (`SaveSnapshotFailure`) Pekko's resequencer expects.
- **Load:** `AbstractMongoSnapshotAdapter` decodes `BsonValue` and would reject the JSONB text the store returns.
- This is the open follow-up **`ditto-postgres-2yg`**; commit `2b44232333` labelled it "partial." Confirmed unaddressed.
- **Fix:** implement the four per-service Postgres snapshot adapters wrapping `PostgresSnapshotAdapter`, set the `snapshot-adapter` override per service under the profile, and wrap `toJsonText`/`extractLifecycle` in `Mono.fromCallable(...)` so serialization failures become failed Futures.

#### C-3. Policy, Connection, and WoT persistence actors hardcode Mongo plugin IDs — never consult the backend provider
*Lenses: actor-wiring, config-hocon-ops, round1-fix-verify (3 confirmations).*
- `PolicyPersistenceActor.java:67,72,156-162` returns `"pekko-contrib-mongodb-persistence-policies-journal"`/`-snapshots`; `ConnectionPersistenceActor.java:166,171,304-310` returns `"...-connection-journal"`/`-snapshots`; `WotValidationConfigPersistenceActor.java:68,73,109-115` returns `"...-wot-validation-config-journal"`/`-snapshots`. Only `ThingPersistenceActor.java:184-190` routes through `backendProvider().getJournalPluginId(...)`/`getSnapshotPluginId(...)`.
- Meanwhile the profile declares `policy.*`/`connection.*`/`wot-validation-config.*` plugin-id mappings (`ditto-postgres-persistence.conf:45-50`) and lists all four entities in `auto-start-journals`/`auto-start-snapshot-stores` (`:99-110`). The profile only *adds* `ditto-postgres-*` blocks; it does **not** redefine the `pekko-contrib-mongodb-persistence-*` blocks (verified by grep). Commit `2b44232333` touched **zero** entity-actor files (verified via `--stat`).
- **Impact:** a policies/connectivity/things(WoT) service including the profile silently keeps writing to MongoDB via the hardcoded IDs while `auto-start-*` eagerly builds Postgres journal+snapshot pools nobody writes to (opening connections, running the SSL boot guard). Silent split-brain; or a hard crash on first persist if Mongo is decommissioned. No error/warning.
- **Fix:** override `journalPluginId()`/`snapshotPluginId()` in all three actors via `backendProvider().getJournalPluginId(<ENTITY_TYPE>)`, mirroring Thing — **or** until then strip `policy`/`connection`/`wot` from the profile's plugin-id map and both `auto-start-*` lists and have the provider `DittoConfigError` for known-unwired entities so the include fails fast.

## 3. High

### NEW (round 1 missed)

#### H-1. Schema bootstrap and `ddl-credentials` are entirely unwired — fresh DB has no tables; DDL-role separation is dead config
*Lenses: config-hocon-ops, security-resources.*
- `PostgresSchemaManager.of(...)` / `.bootstrap()` / `.bootstrapReactive()` have **zero production call sites** — every invocation is in `src/test`. `PostgresPersistenceBackendProvider` (the only boot entry) just builds the runtime pool in `getReadJournal()`; it never bootstraps.
- `getDdlCredentials()` (`DefaultPoolConfig.java:102`) and `DdlCredentialsConfig.isConfigured()` are never consumed by production code; `ConnectionPoolFactory.buildOptions` only layers the runtime `getUsername()/getPassword()`. The shipped `POSTGRES_DDL_USER`/`POSTGRES_DDL_PASSWORD` knobs (`ditto-postgresql.conf:42-48`) do nothing.
- `Migrator.java:295` and `MigratorCli.java:71` tell operators to "run `PostgresSchemaManager.bootstrap()`" — a method no main-source path calls.
- **Impact:** first journal write hits a missing table; the persistent actor fails. The least-privilege DDL story is illusory. (Overlaps the project's known service-side-wiring follow-up but the *unwired bootstrap* is the concrete, untested gap.)
- **Fix:** wire `PostgresSchemaManager` into a real entry point (provider startup hook or `MigratorCli` subcommand) that builds a DDL `ConnectionFactory` from `ddl-credentials` (falling back to runtime per the conf comment) and calls `bootstrap()`, failing boot if neither bootstrap ran nor tables exist; **or** delete `DefaultDdlCredentialsConfig`/`getDdlCredentials()` and rewrite the conf/Migrator error if DDL is intentionally out-of-band.

#### H-2. `fetch-size = 0` defeats backpressure on every unbounded streaming read-journal query — unbounded JVM-heap buffering
*Lenses: reactive-concurrency, pekko-lifecycle, security-resources.*
- `ConnectionPoolFactory.java:87` binds `FETCH_SIZE = 0` globally (default, `PostgresConfig.java:136`); the r2dbc-postgresql driver treats `0` as "no server-side portal — materialise the entire result set" before the Pekko `Source` (`Source.fromPublisher`, `DittoPostgresClient.java:133`) can exert demand. No per-statement `Statement.fetchSize(n)` override exists.
- Genuinely unbounded (no `LIMIT`): `currentPersistenceIds()` (`PostgresPersistenceOperations.java:430-433`), `eventsByTag()` (`:419-427`), `getPidsWithTag(considerOnlyLatest=false)` (`:356-357`). (Verifier correction: `getPidsAbove`/`getJournalPids` and `getNewestSnapshotsAbove` *do* carry `LIMIT $n` and are bounded — the finder over-listed them.)
- **Impact:** on a production journal with millions of pids/events, a single `currentPersistenceIds()` or large-tag `eventsByTag()` buffers the whole result set into heap regardless of consumer demand → OOM / long GC / pinned connection. Cross-backend regression vs Mongo's demand-driven cursor.
- **Tension/fix:** a positive `fetch-size` opens a server-side portal — exactly the PgBouncer-transaction-pooling hazard the `0` default avoids. The fix is route-dependent: bind a positive `Statement.fetchSize(batchSize)` only on the long streaming read-journal statements (or run them on a dedicated non-transaction-pooled connection), and document that `fetch-size=0` disables backpressure.

#### H-5. `PersistencePingActor` cannot wake entities on Postgres — journal tags are never persisted (corollary of C-1)
*Lens: actor-wiring.*
- `PersistencePingActor.java:88,93` streams pids via `getJournalPidsWithTagOrderedByPriorityTag`/`getJournalPidsWithTag`; the read-side GIN SQL is correct but finds no tagged rows because, absent the C-1 event adapter, `toInsert` (`PostgresJournalOps.java:164-177`) sees a bare event (not `Tagged`) and stores `tags = Set.of()`.
- **Impact:** even after serialization is fixed, if the new adapter does not forward `getJournalTags`, always-alive entities are never re-activated after restart and priority pinging is silently empty.
- **Fix:** the new Postgres event adapter's `toJournal` must return `new Tagged(jsonText, getJournalTags(event))`. Resolved together with C-1.

#### H-6. Duplicate-payload mismatch and non-duplicate integrity errors are returned as per-message *rejections*, so the actor silently drops the write instead of stopping
*Lens: pekko-lifecycle.*
- `PostgresJournalOps.reconcileDuplicate` (`:106-128`) / `recoverWrite` (`:88-104`). A *present* `Optional<Exception>` in the result Iterable maps to Pekko `WriteMessageRejected` (recoverable; actor keeps running, event NOT persisted); only a failed overall Future yields `WriteMessageFailure` (actor stops). Two paths wrongly return a present `Optional`: (1) a genuine `(pid,sn)` duplicate whose stored payload/manifest **differs** returns `Optional.of(IllegalStateException)` (`:118-122`) — yet the javadoc (`PostgresJournal.java:54-55`) promises "a genuine mismatch is a fatal failure" (code-vs-contract contradiction); (2) `recoverWrite` routes **every** `R2dbcDataIntegrityViolationException` (incl. NOT-NULL/CHECK, not just PK dups) into `reconcileDuplicate`, where `.defaultIfEmpty(Optional.of(duplicate))` (`:123`) yields a rejection.
- **Impact:** a real sequence-number collision with divergent payload (double-writer / split-brain corruption) is swallowed as benign — event lost, in-memory state diverges from the journal, no restart, no crash signal; a schema/constraint violation is likewise misclassified as recoverable.
- **Fix:** for divergent-duplicate and non-duplicate-integrity cases return `CompletableFuture.failedFuture(...)` (→ `WriteMessageFailure`); reserve the empty `Optional` for the truly-idempotent matching-duplicate only.

#### H-7. `max-idle-time = 0s` documented as "no limit" actually triggers r2dbc's 30-minute idle eviction
*Lens: config-hocon-ops.*
- `ConnectionPoolFactory.java:117,123-128` applies `maxIdleTime` only via `applyIfPositive`, so a `0s` config leaves r2dbc-pool's default (`Duration.ofMinutes(30)`, `ConnectionPoolConfiguration.java:272`) in force. r2dbc requires a **negative** value for "no timeout"; ZERO would mean immediate disposal. Config default is `Duration.ZERO` with javadoc/comment "0 = no limit" (`PostgresConfig.java:132`, `ditto-postgresql.conf:34`), and the getter `getNonNegativeDurationOrThrow` makes a negative value unconfigurable.
- **Impact:** shipped default silently keeps 30-minute idle eviction (the opposite of documented); a quiet-then-bursty service pays full reconnect + TLS handshake (`verify-full`) latency periodically; operators mis-size pools. (`max-life-time` has the same `applyIfPositive` gap but r2dbc's default there *is* NO_TIMEOUT, so only its comment misleads.)
- **Fix:** treat `0s` as the explicit "no limit" sentinel (pass a negative duration when zero), or change the default to a real positive value and correct the docs.

#### H-8. Each plugin builds its own pool — one Postgres service opens up to 3 × `max-size` connections, but the conf sizes `max-size` as the per-service total
*Lenses: config-hocon-ops, reactive-concurrency.*
- `PostgresJournal(Config)` (`:88-94`), `PostgresSnapshotStore(Config)` (`:87-93`), and the provider's read-journal client (`PostgresPersistenceBackendProvider.java:121`) each call `DittoPostgresClient.newInstance(...)` → a brand-new `ConnectionPool` (`ConnectionPoolFactory.createConnectionPool`). All three read the same `ditto.postgresql.pool.max-size`, so one service instance holds journal + snapshot + read-journal = up to **3 × max-size**.
- `ditto-postgresql.conf:27-30` tells operators to set `max-size` to ~200 ("match deployed Mongo maxPoolSize"), ~3× under the truth. With a few replicas this blows past Postgres `max_connections` / PgBouncer pools → connection-refused at scale. (Also relates to lifecycle leak H-9 and the open `ditto-postgres-176` metrics follow-up.)
- **Fix:** share a single `DittoPostgresClient`/pool across journal+snapshot+read-journal of a service (the provider already owns a client lifecycle), or document `max-size` as **per-plugin** with effective-connections guidance and a smaller recommended value.

#### H-9. Pool gauges are never polled for the write-path pools, and even if they were they collapse onto one gauge
*Lens: observability-lifecycle (two coupled findings).*
- **(a) Write pools unpolled:** the only poller start site is `PostgresPersistenceBackendProvider.startPoolMetricsPoller` (`:125`), invoked solely from the lazy `getReadJournal()` path. `PostgresJournal`/`PostgresSnapshotStore` build their own pools but attach **no poller** (verified `grep PoolMetricsPoller`). So `pool_acquired/allocated/idle/pending` reflect only the read-journal pool — which on a write-heavy service may never even be created — making acquire-saturation on the write pools (the failure mode that *stops persistent actors*) invisible.
- **(b) Single-tag collapse:** `PoolMetricsPoller.gauge` (`:106-110`) tags only `engine=postgres`, and every pool is built with the identical name `"ditto-postgres-pool"` (`ConnectionPoolFactory.java:110`). The moment >1 pool is polled, they write the same Kamon instrument (`set` = last-writer-wins, `KamonGauge.java:60-62`) — gauges thrash and cannot represent more than one pool even in principle.
- **Impact:** pool-occupancy observability is effectively non-functional for the production write path. Round 1's "pool gauges wired" fix only covered the read-journal pool.
- **Fix:** start a poller per plugin pool (torn down in `postStop`), give each pool a distinct name, and add a low-cardinality `pool`/`role` tag (`journal|snapshot|readjournal`, NOT pid) to all four gauges. Both sub-fixes must land together. (Overlaps `ditto-postgres-176`.)

#### H-10. Migrator omits the `_journal_seq` high-water-mark table — post-migration recovery reports a too-low sequence number for pruned-then-snapshotted entities
*Lenses: test-quality, sql-schema-migration (related).*
- `MongoMigrationSource.java:35` migrates only `*_journal`/`*_snaps`; `CopyEncoder` (`:43,46`) exposes only `JOURNAL_COLUMNS`/`SNAPSHOT_COLUMNS` — no seq-table encoder. Runtime `readHighestSequenceNr` (`PostgresPersistenceOperations.java:188-198`) = `GREATEST(MAX(journal sn), highest_sn)`; post-migration `_journal_seq` is empty, so the HWM collapses to `MAX(surviving journal sn)`.
- **Impact:** for an entity whose Mongo journal was pruned after snapshotting (Ditto's *normal* cleanup pattern), `MAX(surviving sn)` is below the true HWM → first post-migration recovery reports a too-low `sn`, and the next persisted event reuses an already-issued sequence number → duplicate-key collision or silent stream rewind. `--verify` (`Migrator.java:216-234`) compares only event payload, never the watermark, so it is blind.
- **Fix:** add a watermark-migration step (`INSERT INTO <e>_journal_seq (pid, highest_sn[, deleted_to]) … ON CONFLICT … GREATEST(...)`) from the Mongo per-pid HWM metadata; add a `MigratorTest` seeding surviving rows whose `MAX(sn)` is below the declared watermark and asserting `_journal_seq.highest_sn`.

#### H-11. Snapshot migration cursor `(pid, sn)` is lossy — drops re-snapshots at the same sequence number on a batch boundary
*Lens: sql-schema-migration.*
- `MongoMigrationSource.Cursor` is a 2-tuple `(lastPid, lastSn)` (`:74`); `Migrator.java:193-194` resumes "strictly AFTER" it. Snaps PK is `(pid, sn, written_at)` (`PostgresSchema.java:189`) and by design allows multiple rows per `(pid, sn)`. If a batch boundary lands inside a run of same-`(pid, sn)` snapshot rows, the remaining rows are permanently skipped. `--verify` reads one row per `(pid, sn)` so cannot detect the loss.
- Re-rated high (down from finder's critical): requires both an entity with multiple snapshots at one `sn` (uncommon given Ditto cadence) AND a boundary inside that group. Still silent data loss when it triggers.
- **Fix:** extend `Cursor` to `(lastPid, lastSn, lastWrittenAt)` for snaps, order/resume `readAfter` by `(pid, sn, written_at)`, persist `last_written_at`. Journal keeps the 2-tuple.

#### H-12. COPY text encoder does not reject/escape NUL (` `) — a NUL aborts the whole batch with no resume progress (unrecoverable stall)
*Lenses: sql-schema-migration, security-resources.*
- `CopyEncoder.field()` (`:100-113`) and `arrayLiteral()` (`:122-143`) handle only `\ \t \n \r` / `\ "`; neither handles ` `. Postgres text-format COPY rejects NUL. `flushBatch` throws `CopyBatchException` without advancing the checkpoint when `copied != rows.size()` (`Migrator.java:189-190`), so a NUL-bearing row fails identically on every re-run — a hard wedge. The class javadoc *anticipates* "embedded NUL byte" yet no code detects it.
- Re-rated high (down from finder's critical): requires a source document actually containing ` `; impact is a wedged migration, not corruption. (Round 1 explicitly *rejected* a NUL finding as "not required by COPY spec" — round 2 shows it is real for the unrecoverable-stall mechanism, not silent corruption.)
- **Fix:** detect NUL in `field()`/`arrayLiteral()` and throw a precise per-row error naming `(pid, sn)` before the batch is submitted, or apply a documented sanitisation policy matching the Mongo read path.

### REGRESSION (introduced by `2b44232333`)

#### R-1. `deleteMessagesTo` can *raise* `highest_sn` to `toSequenceNr` on the INSERT path — fabricates a sequence number that was never persisted
*Lens: sql-schema-migration. **Verified: this SQL was introduced by `2b44232333`.***
- `PostgresPersistenceOperations.java:217` — `INSERT INTO <seq> (pid, highest_sn, deleted_to) VALUES ($1, $2, $2) ON CONFLICT (pid) DO UPDATE SET deleted_to = GREATEST(...)` with `stmt.bind(1, toSequenceNr)`. On the INSERT path (no prior `journal_seq` row), this sets `highest_sn = toSequenceNr`. The class javadoc at `:48` asserts "deletes only ever move `deleted_to`, never `highest_sn`" — the INSERT branch violates the stated invariant. Confirmed introduced by the remediation commit (the file is in `2b44232333 --stat`; the `VALUES ($1, $2, $2)` line is present in the current tree, verified verbatim).
- **Why the green test misses it:** `deleteMessagesToMovesDeletedToNeverHighestSn` (`PostgresJournalTest.java:101-113`) asserts only the SQL string `doesNotContain("SET highest_sn")` — it checks the UPDATE branch and never the INSERT `VALUES ($1, $2, $2)` clause.
- **Impact:** if `deleteMessagesTo` ever runs before any `insertEvents` created the HWM row for that pid (Pekko can invoke delete with a snapshot sn / `Long.MAX_VALUE` bound), `readHighestSequenceNr` returns the fabricated value via `GREATEST(...)`.
- **Fix:** insert `highest_sn = 0` (or `COALESCE(MAX(sn),0)` from the journal) on the INSERT path and only ever touch `deleted_to`: `VALUES ($1, 0, $2) ON CONFLICT (pid) DO UPDATE SET deleted_to = GREATEST(seq.deleted_to, excluded.deleted_to)`. Add a test asserting the INSERT VALUES clause, not just the UPDATE SET.

#### H-13. No end-to-end coverage for concurrent same-pid writes, hard-crash resume, or multi-entity (Policy/Connection/WoT) recovery
*Lens: test-quality.*
- `PostgresPluginLifecycleIT.java:110-144` boots a single actor / single pid for `things` only and stops with a graceful `PoisonPill` (`:133`) — no hard crash mid-write, no concurrent same-`(pid,sn)` race; grep for `policies|connections|wot` in the lifecycle IT returns nothing. The duplicate-reconcile decision (H-6) and per-entity wiring (C-3) are unvalidated end-to-end.
- **Fix:** add ITs for N concurrent `writeMessages` on the same `(pid,sn)` (identical vs differing payload → idempotent success vs fatal), a parametrized lifecycle IT over `{things, policies, connections, wot}`, and a crash-resume case.

## 4. Medium

### NEW

- **M-1. `inTransaction` cancellation closes the connection mid-transaction without an explicit ROLLBACK** *(reactive-concurrency)* — `PostgresPersistenceOperations.java:506-516`. The 3-arg `Mono.usingWhen` runs `Connection::close` on cancel, but the explicit `rollbackTransaction()` lives in `.onErrorResume` on the closure, firing only on **error** — never on **cancel** (downstream unsubscribe / write-Future drop / actor stop mid-write). A connection can be recycled "idle in transaction," holding row locks until pool reset. *Fix:* use the 4-arg `usingWhen` and rollback-then-close on both the error and cancel arms.
- **M-2. Read-journal `getLatestJournalEntries` is N+1 and each inner query is an unbounded `fetch-size=0` fetch** *(reactive-concurrency, security-resources)* — `PostgresReadJournal.java:114-123` does `currentPersistenceIds().flatMapConcat(pid -> currentEventsByPersistenceId(pid,0,MAX).fold(keep-last))`; the inner SQL (`PostgresPersistenceOperations.java:403-413`) has no `LIMIT`, so it reads every event of every entity to keep one row per pid. Sole production caller is `ConnectionIdsRetrievalActor` (connectivity), so it is reachable in production; a single long-history pid can blow the heap. *Fix:* `SELECT DISTINCT ON (pid) … ORDER BY pid, sn DESC` (the pattern already used in `getNewestSnapshotsAbove`).
- **M-3. Per-plugin pools are disposed only on actor `postStop`, not registered with `CoordinatedShutdown`** *(reactive-concurrency, observability-lifecycle, round1-fix-verify)* — `PostgresJournal`/`PostgresSnapshotStore` build their own clients and dispose them only in `postStop()`; only the provider's read-journal client is registered with `CoordinatedShutdown` (`PostgresPersistenceBackendProvider.java:141-148`). Pekko does not guarantee a plugin actor's `postStop` runs before dispatcher teardown → pool leak on rolling restarts. Additionally `DittoPostgresClient.close()` is fire-and-forget (`:200-203`); the awaitable `disposeLater()` (`:205-210`) is unused, so the shutdown phase does not wait for drain → connection-reset noise / half-open transaction window. *Fix:* register each plugin client with `CoordinatedShutdown` and return `disposeLater().toFuture()` from the shutdown task (or share one pool — see H-8).
- **M-4. `read-journal.entity` defaults to `things` for every service** *(config-hocon-ops)* — `ditto-postgres-persistence.conf:53-55` / `PostgresPersistenceBackendProvider.java:82,168-175`. A policies/connectivity service that forgets `POSTGRES_READ_JOURNAL_ENTITY` binds cleanup/ping/historical queries to `things_journal`/`things_snaps`; the provider validates the value is a *known* entity but cannot detect it is the *wrong* one. No service config overrides it. *Fix:* remove the default; require explicit `read-journal.entity` per service and `DittoConfigError` if absent when the provider is active.
- **M-5. ## 6. Residual Risk — what round 2 could NOT fully verify

- **Real-cluster load / OOM thresholds.** H-2 (`fetch-size=0` unbounded buffering), M-2 (N+1 latest-entries), and H-8 (3× connection budget) are confirmed by code shape but their *trigger points* (millions of pids, large `always-alive` tag fan-out, replica count × `max_connections`) were not measured against a populated DB. Load spikes against real Postgres remain outstanding (noted as an open follow-up in project memory).
- **Multi-service deploy.** C-3 (entity-actor wiring) and M-4 (`read-journal.entity` default) were verified statically; no actual policies/connectivity/WoT service was booted on the Postgres profile to observe the split-brain / wrong-table-cleanup behaviour end-to-end. H-13 is precisely the missing test for this.
- **Testcontainers-gated ITs may skip in CI (L-3).** The "124 unit + 28 IT green" baseline is only meaningful on a Docker-equipped runner; on a Docker-less runner the entire IT matrix skips silently and still reports green. Round 2's confidence in the IT-covered paths (lifecycle/recovery, GIN gate, TOAST, pool-timeout, PgBouncer) is therefore conditional on Docker actually being present in the verifying CI.
- **PgBouncer transaction-pooling interaction with a positive `fetch-size`.** The H-2 fix is route-dependent because a server-side portal conflicts with transaction pooling; the correct boundary between read-journal queries (need portals) and write-path queries (must stay pooling-safe) was reasoned about but not validated behind a real PgBouncer.
- **Crash-during-COPY recovery (M-8/M-9/H-12).** The unrecoverable-stall mechanisms were proven from control flow, but no fault-injection run (kill -9 between COPY-commit and `saveProgress`, NUL-bearing document, sibling-failure interrupt) was executed against a real migration.
